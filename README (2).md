# Supplier Integration Service

Учебный backend-проект уровня **Junior+** для подготовки к собеседованию на Python backend-разработчика, который занимается интеграциями с внешними системами.

> **Главная цель:** не получить готовый репозиторий, а **самостоятельно написать и понять код**. Codex выполняет роль наставника, интервьюера и code reviewer.

## 1. Бизнес-контекст

Компания работает с несколькими поставщиками. Каждый поставщик предоставляет товары через собственный HTTP API. Нужно разработать сервис, который хранит сведения о поставщиках, забирает и проверяет данные, синхронизирует товары в PostgreSQL, предоставляет REST API и отчёты, сохраняет историю синхронизаций.

Сначала создаём небольшой **mock API поставщика** внутри учебного окружения, чтобы не зависеть от сторонних сервисов. Позже можно подключить публичное внешнее API.

## 2. Технологии

- Python 3.12+
- FastAPI + Uvicorn
- Pydantic v2 + pydantic-settings
- PostgreSQL
- SQLAlchemy 2.x (async ORM, `AsyncSession`) + asyncpg
- Alembic
- HTTPX (`AsyncClient`)
- Pytest + pytest-asyncio
- Docker + Docker Compose
- Ruff, Git, Bash
- Стандартный модуль `logging`

**Не добавлять без необходимости:** Redis, Celery, Kafka, Kubernetes, микросервисы, JWT. Сначала сделать надёжный понятный монолит.

## 3. Функциональные требования

### 3.1. Поставщики

| Метод | URL | Назначение |
| --- | --- | --- |
| `POST` | `/api/v1/suppliers` | Создать поставщика |
| `GET` | `/api/v1/suppliers` | Получить список |
| `GET` | `/api/v1/suppliers/{id}` | Получить одного |
| `PATCH` | `/api/v1/suppliers/{id}` | Частично изменить |
| `DELETE` | `/api/v1/suppliers/{id}` | Удалить (правило удаления согласовать перед реализацией) |

Поля поставщика: `id`, `name`, `base_url`, `is_active`, `created_at`.

### 3.2. Товары

| Метод | URL | Назначение |
| --- | --- | --- |
| `GET` | `/api/v1/products` | Список с пагинацией, фильтром по поставщику, сортировкой |
| `GET` | `/api/v1/products/{id}` | Получить товар |

Поля товара: `id`, `supplier_id`, `external_id`, `name`, `price`, `currency`, `stock`, `updated_at`.

Правила: цена — `Decimal`/`NUMERIC`, не `float`; `stock >= 0`; пара (`supplier_id`, `external_id`) уникальна.

### 3.3. Синхронизация

| Метод | URL | Назначение |
| --- | --- | --- |
| `POST` | `/api/v1/suppliers/{id}/sync` | Запустить синхронизацию |
| `GET` | `/api/v1/suppliers/{id}/sync-history` | История запусков |

При синхронизации сервис должен:
1. Проверить существование и активность поставщика.
2. Запросить его API через HTTPX с таймаутом.
3. Проверить ответ Pydantic-схемой.
4. Добавить новые и обновить существующие товары по `external_id` внутри поставщика (повторный запуск не должен создавать дубликаты).
5. Зафиксировать результат: `started_at`, `finished_at`, `status`, `created_count`, `updated_count`, `error_message`.
6. Корректно обработать недоступность поставщика, ошибочный HTTP-статус, невалидный JSON и ошибки БД. Не сохранять частично повреждённые данные.

Для первой версии синхронизация выполняется **прямо в HTTP-запросе**; фоновые задачи — только отдельным улучшением. Секреты и пароли не должны попадать в логи.

### 3.4. Отчёты

`GET /api/v1/reports/products` — количество товаров и суммарный остаток по поставщикам. Реализовать через SQL `JOIN`, `GROUP BY`, `COUNT`, `SUM`, затем разобрать `EXPLAIN ANALYZE` и индексы.

### 3.5. Технические требования

- Использовать корректные HTTP-методы и статусы: `201`, `200`, `204`, `404`, `422`, при необходимости `409`/`502`.
- Схемы запросов и ответов отделять от моделей ORM.
- Разделить API-роутеры, бизнес-логику, доступ к БД и интеграционный HTTP-клиент.
- Конфигурацию хранить через env-переменные (`.env.example`, без секретов в Git).
- Менять схему БД через Alembic, не через `create_all` в рабочем приложении.
- Обеспечить Swagger/OpenAPI по `/docs`.
- Добавить понятные логи, тесты, скрипты запуска и инструкции в README.

## 6. Правила работы Codex — ОБЯЗАТЕЛЬНО

Пользователь пока плохо знает Python и **хочет писать проект своими руками**.

1. **Не создавай весь проект и не генерируй готовое решение задачи по умолчанию.**
2. Работай как **технический наставник**: одна небольшая задача за раз.
3. Перед заданием кратко объясни нужные понятия и покажи маленький **несвязанный с задачей** пример синтаксиса.
4. Сначала дай ТЗ, критерии приёмки и способ самостоятельной проверки. **Не пиши решение**, пока пользователь прямо его не запросит.
5. Когда пользователь присылает код, сделай code review: баги, читаемость, типы, HTTP, SQL, обработка ошибок; объясни причины замечаний.
6. При затруднениях двигайся по ступеням: **наводящий вопрос → подсказка → маленький фрагмент → полное решение только по просьбе**.
7. Не меняй файлы автоматически без явного запроса. Если Codex может редактировать репозиторий, сначала предложи изменения и дождись разрешения.
8. После каждого этапа задай 3–5 вопросов в стиле собеседования Junior+.
9. Объясняй новые Python-концепции по мере появления: `dict`, `list`, `None`, type hints, классы, исключения, `with`, декораторы, `async/await`.
10. Не усложняй архитектуру «на вырост»; отмечай, что является обязательным, а что улучшением.
11. Общайся **на русском**, технические названия оставляй на английском.
12. В конце каждого шага кратко фиксируй: **что сделано, что проверить, что дальше**.

## 7. Первая задача (начинаем с неё)

**Этап 1.** Создать локально минимальное FastAPI-приложение с тремя маршрутами, без БД:

- `GET /health` → `{"status": "ok"}`.
- `GET /suppliers` → список из двух поставщиков, хранящийся в Python-списке.
- `GET /suppliers/{supplier_id}` → поставщик по числовому ID или `404`.

Критерии приёмки:
- `/suppliers/1` возвращает первого поставщика.
- `/suppliers/999` возвращает `404`.
- `/suppliers/abc` возвращает `422`.
- Документация доступна по `/docs`.

**Первое действие Codex:** объясни, какие знания нужны для этого шага, и дай инструкцию по установке окружения **без написания кода приложения**. Затем попроси пользователя показать свою реализацию для ревью.

## 8. Definition of Done проекта

Проект завершён, когда он запускается через Docker Compose; миграции создают структуру PostgreSQL; CRUD, синхронизация, история и отчёты работают; негативные сценарии обработаны; тесты проходят; README описывает запуск и API; пользователь может объяснить архитектуру и ключевые решения на собеседовании.
